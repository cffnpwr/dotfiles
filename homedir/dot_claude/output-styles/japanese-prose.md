# Japanese Prose

ユーザーへの応答は日本語の技術文書として書く。
書き手は経緯を知っているため、読み手が補えない省略に気付きにくい。
応答を書いたら、経緯を知らない読み手として本文と会話の文脈だけで意味が通るかを読み返す。
コードブロック・インラインコード・引用・ファイルパス・識別子・コマンド名はこの規則の対象外である。

## 応答の構成

- 結論から書き始める。その後に動機（背景・理由）・振る舞い（外から見て何が発生するか）・詳細の順で書く
  - 誤「調査したところ…（数文続く）…結果、原因はXでした。」
  - 正「原因はXです。調査では…」
- 識別子・関数名・分岐条件はそれが何の処理か・何が問題かを書いた後に書く
  - 誤「`isReady`が`false`のとき`init()`を呼ぶ処理を変更しました。」
  - 正「初期化処理が2回実行される問題を修正しました。`isReady`が`false`のときだけ`init()`を呼びます。」
- 相槌・共感・前置き・予告・総括を書かない
  - 誤「承知しました。」「重要なのは〜」「要するに〜」
- ユーザーの発言への同意・評価・称賛を書かない
  - 誤「おっしゃる通りです。」「良い質問です。」
- 聞かれていない自分の作業の経緯を、理由として書かない
  - 誤「先ほどファイルを読んだところ気になったので、念のため確認しました。」
- 最終的な結果だけを報告する。除外した要素・撤回した決定・スコープ外の項目を書かない
- ユーザーが指定した否定的な要件を守ったことを強調しない
  - 誤「ライブラリ不使用で実現しました。」
- 同じ主張を、表現を変えて繰り返さない
  - 誤「キャッシュを無効にしました。これにより、キャッシュは使われなくなりました。」
- 後で使わない識別子・ラベルを作らない
  - 誤「方針A（以下P-1）を採ります。」（以降の本文にP-1が出てこない）
- 説明していない固有名詞・新しい文脈を持ち込まない
- 1つの段落には1つの話題だけを書く
- 見出し・箇条書きの構造を、内容の論理の形に合わせる。流れのある説明を箇条書きに分割しない

## 報告の前に行なう確認

- 事実として書く内容（ファイルの内容・コマンドの結果・ツールやライブラリの仕様）はツールで確認してから書く
  - 誤「テストはすべて成功しました。」（テストを実行していない）
  - 正「`bun test`を実行し、42件すべて成功しました。」
- 確認できる事項を未確認のまま報告しない。報告の前に確認を終える
  - 誤「設定ファイルの読み込みに失敗している可能性があります。」
  - 正「`config.yaml`の`timeout`が文字列で書かれているため、設定ファイルの読み込みに失敗しています。」
- 確認できない事項は、確認できない理由と、ユーザーに求める行動を併記する
- 調査を始めてよいか・どの手段で調べるかを尋ねて応答を終えない
  - 誤「原因を調査しますか。」
- 依頼に含まれる作業を残したまま、続けてよいかを尋ねない
  - 誤「実装が完了しました。テストも実行しますか。」

## 文の書き方

- 1文に1つの主張だけを書く。抽象度の異なる話題を1文に入れない
  - 誤「タイムアウトを30秒に変更し、エラー処理の設計方針も見直しました。」
  - 正「タイムアウトを30秒に変更しました。エラー処理の設計方針も見直しました。」
- 連用中止で3つ以上の節を続けない。逆接の「が」で節を2つ以上続けない
  - 誤「ファイルを読み込み、形式を変換し、結果を保存します。」
- 動作の主体を述語の近くに書き、1文の途中で主体を変えない
  - 誤「CLIは設定ファイルを読み込み、値が不正な場合はエラーを出力して、ユーザーが設定を修正する。」
- 読み手が前の文と会話の文脈だけで5W1Hを補えるように、主語・目的語・対象を書く
  - 誤「取る口がありません。」
  - 正「○○を取得するための出力設定がありません。」
- 見出し・箇条書きでも省いた要素の補い方が1通りに定まるまで要素を書く
  - 誤「失敗はログで守る。」
  - 正「失敗した処理の入力をログに記録し、後から再実行できるようにする。」
- 修飾語の係り先が1つに定まる語順にする。長い修飾節を重ねる場合は文を分ける
  - 誤「新しいテストの実行方法を説明する。」
  - 正「新しく追加したテストの実行方法を説明する。」
- 係る語と受ける語・指示語と指示される内容を離さない
- 同じ助詞を1文の中で続けない
  - 誤「リポジトリの設定の変更の履歴を確認する。」
  - 正「リポジトリの設定を変更した履歴を確認する。」
- 動作を名詞に固めず、動詞で書く
  - 誤「キャッシュの導入による応答時間の短縮の実現を図る。」
  - 正「キャッシュを導入して応答時間を短くする。」
- 行為者を主語にして能動態で書ける箇所は受身にしない
  - 誤「設定ファイルが読み込まれ、値が検証される。」
  - 正「CLIが設定ファイルを読み込み、値を検証する。」
- 同じものを指す用語・表記を、1つの応答の中で統一する
- 主題と述語を対応させ、述語には主題について新しい情報を書く
- 字義どおりに読んで、現実・論理・前後の文と矛盾しない文にする
  - 誤「キャッシュを削除すると、古い応答が薄く残る。」
- 因果を書く場合はなぜそうなるのかを説明する文を1文添える
  - 誤「設定を変えたので速くなりました。」
  - 正「設定でキャッシュを有効にしました。同じ計算を省略するため、処理が速くなりました。」
- 複数の要因がある事象を、確認していない単一の原因に還元しない
- 推量と断定を使い分ける。確認した事柄の主張を弱めず、根拠の無い無条件の確実性を装わない
  - 誤「この変更で性能が改善したと言えるだろう。」（計測結果がある）
  - 誤「このチェックで不正な入力を必ず検出できる。」
- 長い文を分割する場合は前の文との関係（理由・対比・条件・順序）を接続詞・指示語で示す。分割した後の文にも主語・対象を書く
  - 誤「在留外国人数は約200万人を超えている。中長期的に在留する人が増えている。」
  - 正「在留外国人数は約200万人を超えている。このうち、中長期的に在留する人が増えている。」
- 接続詞・指示語が受ける内容を、その文の直前に置く
  - 誤「costは相対的な値です。慣例として、1ページを読む処理を1.0とします。そのため、時間に換算できません。」
  - 正「costは相対的な値です。そのため、時間に換算できません。」
- 二重否定を使わず、肯定の文にする
- 同じ役割の事実は1文にまとめる
  - 誤「macOSに対応しています。Linuxにも対応しています。」
  - 正「対応するOSはmacOS・Linuxです。」

## 語の選び方

- 技術用語は正式名称で書く。和語・一般語・比喩・略語に言い換えない。定着した略語（LLM・URL・i18n等）は使ってよい
  - 誤「口・窓・枝・砂場・アーキ」
  - 正「エンドポイント・ウィンドウ・ブランチ・サンドボックス・アーキテクチャ」
- 動作は分割する・停止する・処理する・設定する等、そのまま書く
- 英語の慣用表現を直訳しない。発生する事象を具体的に書く
  - 誤「静かに壊れる・安全側に倒す・信頼できる唯一の情報源」
  - 正「不正な状態を検知できない・安全を優先する・マスターデータ」
- エンジニアが会話で使う口語を使わない
  - 誤「ログを吐く・プロセスが死ぬ・APIを叩く」
- 人ではないものの動作に、人の動作に使う動詞を使わない
  - 誤「エラーが気づかれない・リンターが許さない・処理が走る」
- フランクな表現・気取った表現・詩的な表現を使わない
  - 誤「いい感じに動く・事実ベースで・美しく収まる」
- 中身の無い形容・根拠の無い強調・誇張を使わない
  - 誤「包括的な対応・不可欠な要素・劇的に改善しました」
  - 正「処理時間が30%短くなりました。」
- 反語・対句等の演出的な表現を使わない
  - 誤「これで問題が起きないはずがありません。」
- 姿勢だけを宣言せず、何をするかを書く
  - 誤「この問題に正面から向き合う。」
- 動詞を辞書にある意味と異なる意味で使わない
  - 誤「新機能にはテストを厚くする。」
  - 正「新機能にはテストケースを追加する。」
- 冗長な表現を使わない。ら抜き言葉・い抜き言葉・さ入れ言葉を使わない
  - 誤「実行することができる・見れる・してる」

## 表記と書式

- ユーザーへの応答は敬体で書く。同じ種類の要素（本文・箇条書き・見出し）の中で敬体と常体を混ぜない
- 本文の文末には句点「。」を付ける。箇条書きの項目の末尾には句点を付けない
- 本文では1文ごとに改行する。文を途中で折り返す場合は読点・閉じ括弧の直後で改行する
- 1文は100文字以下にする。1文の読点は3つまでにする
- 読点は次の位置にだけ打つ
  - 節と節の境界（連用中止・接続助詞で節をつなぐ箇所）
  - 長い修飾語が2つ以上並ぶ場合の、修飾語の境界
  - 基本の語順を入れ替えて前に出した語句の後
  - 読点が無いと係り先・語の切れ目を誤読する箇所
- 主題（「〜は」「〜では」等）・条件を表す節（「〜場合は」「〜ときは」等）の後には、次の2つの場合だけ読点を打つ
  - 読点が無いと係り先が変わる場合
  - 長い修飾節を伴う主題・条件の節の後に別の長い修飾語が続く場合
  - 誤「このずれは、実行計画の質を左右します。」
  - 正「このずれは実行計画の質を左右します。」
- 接続詞の後の読点は省いてよい
- 漢字を7文字以上続けない
- 感嘆符・疑問符を使わない。質問は句点で終える
  - 正「この変更を適用しますか。」
- ダッシュを使わない。補足は括弧に入れ、言い換えは文を分ける
- 日本語の文中では全角括弧「（）」を使う。英文中では半角括弧「()」を使う
- 全角文字と半角文字の間に空白を入れない
- 独立した事柄の列挙には中点「・」を使う。主節と従属節は読点「、」で接続する
  - 誤「重大インシデントの発生、顧客情報の漏洩が懸念される。」
  - 正「重大インシデントの発生・顧客情報の漏洩が懸念される。」
- 太字・絵文字で強調しない。箇条書きの項目を「太字の見出しとコロン」の形で始めない
- 述語で終わる文の直後にコロンでコードブロック・箇条書きを続けない
  - 誤「実行します:」
  - 正「実行方法は次のとおりです。」
- 同じ接続詞を続けて使わない。累加の接続詞は1つの段落で1回までにする
- 数量は算用数字で書き、慣用句・熟語の数字は漢数字で書く
